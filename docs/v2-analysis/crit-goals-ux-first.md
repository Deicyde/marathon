# Goals-Coverage Critique — Marathon v2 "Code Tinder" design

## Goal 1: Claude+Aristotle integration — **B+**
The division of labor is sound and mostly inherited: Aristotle proves/edits (steered by hermes_watcher, reattachable, `ask()` continuations), Claude drafts/rates/juries/referees, and the new jury (C5) and impact-analysis prompts give Claude real new judgment work. C7's bundle caching and the orchestrator's semaphore finally exploit Aristotle's fleet concurrency. Two gaps: **(1)** the bounce-back path in C2 feeds cherry-pick *conflicts* to `project.ask()` — but conflict resolution is general-purpose code editing, exactly the task the goals say Aristotle is *not* good at. A Claude pre-pass (rebase the diff, then resubmit) is the natural design and is unstated. **(2)** The goal mentions Claude "managing large pools of agents"; here pool management is a Python daemon, with Claude nowhere in scheduling/triage decisions (e.g., deciding whether a failed job needs a new prompt vs. a retry). Defensible, but unargued.

## Goal 2: Hands-off + minimal human-verified surface — **B-**
The design has a *credible filter* but a weak *minimizer*. Credible: jury thresholds + `#print axioms` + matcher as a hard landing gate, "jury-fail never reaches the human," dependency-ordered cards, verification keyed to (declaration, SHA) rather than diffs, and an explicit refusal to auto-verify. That genuinely reduces wasted human reads (the PR-#81 class). But the goal asks for something stronger: marathon should *compute the minimal trusting set* — "only the key definitions/theorems a human needs to read." Nothing here does that. The deck still deals one card per declaration; a 300-lemma chapter is 300 cards, just better-sorted. The dep engine (C6) is the obvious substrate for a spec-boundary mechanism (verify top-level statements + their transitive *definitional* dependencies; auto-trust internal lemmas whose statements are never load-bearing), and the design never draws that conclusion. Also missing: **semantic invalidation**. (decl, SHA) keying plus impact analysis catches *build-breaking* upstream changes, but a dependency's definition can change meaning without breaking consumers — verified statuses silently go stale. Finally, "point marathon at an axiom or an arbitrary repository" appears only as textbook/chapter job kinds; the axiom-driven entry point is unaddressed.

## Goal 3: In-depth per-declaration review — **A-**
Survives intact by construction: card bodies kept verbatim, `o` deep-dive into the existing coreviewer chat, reject notes verbatim-to-Aristotle preserving the Claude-bypass, GitHub issues retained as the durable record. Two erosions worth flagging: the GitHub projection is **one-way**, so the currently-practiced workflow of driving verdicts from issue comments (or a second reviewer working purely in GitHub) dies silently — verdicts now exist only via the local TUI on the operator's machine. And for full-control users, machine output now lands on `marathon/next` *before* human review; a "nothing lands unverified" per-chapter mode is not offered. Goal 3 users may want exactly that.

## Goal 4: Long-timescale, large-context referee — **D+**
Vestigial. The referee appears as: a job `kind` in the orchestrator, a consumer of deception tags (C6), and a calibration client of the demoted 7-axis rater. That is today's referee — a one-shot Claude call that rewrites a notes file (`referee.py:387-524`, advisory machine-tail only) — with marginally better inputs. The goal asks for an *enforcing* actor with project-wide context. Unspecified: **cadence/triggers** (after every N landings? per chapter close?), **context strategy** (the current 400k-char repo dump won't scale to "an entire textbook"; no retrieval/summarization plan), and above all **authority**: the landing gate is `lake build` + audit + per-decl jury — there is no cross-cutting style/doc/naming/duplication check anywhere in the pipeline, no referee veto on landings, and no mechanism for the referee to *open refactor jobs* (the orchestrator has no refactor job kind). "Idiomatic, reusable, navigable" is enforced by nothing. This is the one goal where the design says "existing roles, unchanged" about the component the goal says must change most.

## Goal 5: Seamless UX — **A-**
The strongest section, and it earns it: integration branch kills branch-serialization and manual merges by construction; the dep engine answers the inter-issue dependency question with elaborator facts, not heuristics; requeue-with-backoff removes human-as-retry-logic; the deck's ready-gating plus dep ordering is real "Code Tinder." Remaining holes: **deck starvation** — a rejection blocks its dependents for one Aristotle round (20–45 min) *plus* a serial `lake build` landing; the "orchestrator is already running k+1's fixes" claim is false for rejection-triggered work, which by definition starts at judge time. A long dependency chain degrades back to today's wait-loop, and the design neither quantifies refill latency nor mitigates it (e.g., speculative pre-builds of likely-reject cards). **Landing-queue throughput** is unanalyzed: serial cherry-pick + `lake build` per landing on a Mathlib-scale repo can be the bottleneck under concurrency 4–6; no batching of compatible landings is mentioned.

**Summary:** G5 and G1 are designed; G3 is preserved with a one-way-sync regression; G2 filters well but never actually minimizes the verified surface; G4 is named, not designed.
