## Feasibility critique: Marathon v2

The deck is the right north star and (a)/(b)/(c) attack real, documented pain. But the design assumes away five hard problems and sequences two others wrong.

**1. The concurrency math is unvalidated — and it's the load-bearing claim.** C1's payoff ("7 Ch.12 issues become an overnight batch") assumes Aristotle tolerates 4–6 concurrent *agent tasks*. The only evidence cited is `backfill-wall-time`, which parallelizes read-only metadata fetches. The aristotle-web report says the API terms forbid "concurrent sessions in excess of any limits established by Harmonic," with limits undocumented and behind login. If the real limit is 1–2, the orchestrator is scaffolding around a serial pipe. *Fix:* confirm limits with Harmonic before building C1; design the scheduler around an externally-set semaphore with 429/quota handling, and ship Phase 2 only after a 2-concurrent soak test. Same audit for the Claude side: N jobs × whole-repo reviewer prompts × per-EDITING_FILE steering calls all bill one Max subscription — quantify before assuming N>2.

**2. C5's faithfulness jury contradicts the copyright firewall.** autoform's jury judges faithfulness *against the book*; Marathon's Claude deliberately never sees the `.tex` (autoform-relation §2, geo-local §1). The only substitute is the issue body's informal statement — flagged "LLM-rendered, verification pending." A jury grading LLM output against LLM renderings is circular, and faithfulness is the 0.4-weight gate. *Fix:* drop faithfulness from the machine gate (humans own it — that's the deck's job) and ship only proof_integrity + axiom check + deception tags, which need no source text. That's the honest 80%.

**3. The landing queue is the new serial bottleneck, and its conflict story doesn't work.** Every landing runs `lake build` (10–30 min on this Mathlib-pinned repo); proving concurrency 4 feeding a serial 20-min gate caps throughput at ~3 landings/hour regardless. Worse: `formalization.yaml` and `.marathon/PromptLog.md` are committed *every iteration* (`post_pipeline.py:310-346`), so consecutive cherry-picks conflict on metadata by construction. And the bounce mechanism — "build log as continuation context for `ask()`" — misunderstands `ask()`: it resumes the server-side session on the *old uploaded bundle*; Aristotle cannot see the rebased `next` tree, so it will "fix" a conflict in a world that no longer exists. *Fix:* regenerate metadata files at landing time (not in worktrees); batch landings bors-style; on conflict, do a mechanical rebase locally and only on failure resubmit *fresh* from the updated worktree with the conflict diff in the prompt. Also budget worktree disk/cache: N worktrees × Mathlib `.lake` artifacts is real money in disk and cold-build time — shared cache strategy is hand-waved as "cached toolchain."

**4. Phase ordering ships optimistic concurrency without the collision detector.** C6's decl-overlap check is what makes concurrent jobs safe, but it's Phase 5 while concurrency arrives Phase 2 and the shared branch Phase 3. The #50→Ch12 incident says overlapping jobs *will* collide. *Fix:* pull a crude overlap check forward into Phase 2 — file-path intersection of job focus sets is regex-grade but catches the #50 class; the Lean metaprogram (which must also build against the vendored `Mathlib_4_30` pin and behave sensibly on 386 sorry-bodied decls — untested) can replace it later.

**5. "Red main impossible by construction" breaks on the first human commit.** GeometricAnalysis history shows constant hand-fix commits directly to main (geo-github §1). One such commit and `next` no longer fast-forwards. Also: the hard build gate meets a repo where main was red for four days and statement-verification is the frontier — a jury/build gate tuned for "done" code will starve the deck (only 2 of 78 decls are sorry-free). *Fix:* route human fixes through the same queue (cheap once it exists), auto-rebase `next`, add a "tree-wide sweep" job kind for signature changes, and make gates statement-mode-aware.

**6. Migration breaks the live workflow in two undeclared places.** (a) The bootstrap/audit coreviewer briefings literally instruct the agent to hand-edit `config.toml`'s `[[chapters]]` (`chapter_sessions.py:106,151`); C3 makes the ledger own that mapping but the plugin briefings aren't in any "touches" list — `/marathon:review:bootstrap-chapter` silently desyncs. (b) One-way GitHub projection drops verdicts the operator records on GitHub directly (they demonstrably do), and gitignoring SQLite removes the cross-machine durable queue that git-tracked `state.json`, for all its faults, provided. *Fix:* update the agent briefings in C3's scope; add an inbound reconcile poll (labels/verdict comments → ledger) — you already need it for drift repair.

**7. Two sizing flags.** `refine.py` is 1,404 lines entangled with `RefineState`, branch hacks, and cwd assumptions — "90% there" is optimistic; C1 is L+. C4's TUI with live event streaming, dep view, and embedded editor is L, not M. And C5's "jury-fail never reaches the human" needs an attempt cap that escalates a *stuck* card to the deck, or a never-passing statement burns Aristotle hours invisibly — the exact failure the twelve-iteration `coordinateCoframe` saga predicts.

**Keep:** C7/C8 unconditionally; the ledger; statement-keyed verification. **Prove first:** Aristotle concurrency, landing throughput. **Cut:** machine faithfulness judging.
