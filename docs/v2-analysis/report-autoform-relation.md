# autoform ↔ marathon: architecture map and integration report

## 1. The autoform-bot pipeline

**autoform-bot** (`/Users/jack/Desktop/LEAN/autoform-bot`) is a multi-agent Python engine (paper: "Formalizing Mathematics at Scale," Cabannes et al.) that turns a LaTeX/Markdown textbook into a verified Lean 4 + Mathlib repo. **autoform-bot-plugins** is a fork that repackages it as a Claude Code plugin: commands `/autoform:{extract,orchestrate,formalize,eval,review}`, agent definitions as markdown (`plugins/autoform/agents/`), and three skills (lean-conventions, formalization-workflow, eval-rubrics) lifted from the engine's `skills/` and `rubrics/`. Each command defaults to driving the Python engine; `--backend native` runs a lighter in-session loop (TodoWrite as the DAG store).

**Stage 1 — Statement extraction** (`autoform/statement_extraction/`). Book files are split into overlapping line chunks (500/50 default); k=4 independent single-turn extractor agents per chunk extract explicitly labeled statements; unanimous consensus auto-accepts, a reviewer agent arbitrates disputes, and a merger agent deduplicates across chunk overlaps by mathematical content. Output: **`targets.yaml`** — a list of `FormalizationTarget` records (`name`, `description`, `kind`, `location`, plus `lean_declaration`/`lean_file` filled downstream by eval) — plus `review.yaml` (dispute audit trail) and `cost.json`.

**Stage 2 — Orchestration** (`autoform/bot/`). Rank 0 runs a coordinator: a persistent **orchestrator** agent (Opus, 1M context, history survives restarts via trace resume) plans a task DAG in `ItemTracker` (persisted as `dag.json`) — one task per statement, `depends_on` edges, flavors `task`/`meval`/`decomposition`. A `DAGRunner` dispatches ready tasks over ZMQ (SLURM multi-node) to **worker** agents in isolated git worktrees (optionally racing 3–5 agents per task). After `lake build` passes, a **correctness reviewer** + **quality inspector** must both approve; approved diffs go to a bors-style **merge queue** (batch, cherry-pick, build, fast-forward). Post-merge, a **merge matcher** agent maps the diff to affected book targets, an LLM jury grades them, the **goal tracker** (`goals.json` — per-target status/score, the book-level progress ledger) updates, and a **merge-eval triage** agent auto-creates granular `meval-fix-*` tasks (one per sorry, per axiom issue, per faithfulness problem). Failed tasks trigger a persistent **trace analyzer** that writes per-task skill guides (`skills/tasks/{id}/guide.md`) consumed by the next attempt. Whole-book progress = `goals.json` + `dag.json` + round-stamped reports/traces in `archive/`; runs resume by omitting `--fresh`. An **escalation** tool surfaces blockers to the human operator; a web **visualizer** shows everything.

**Stage 3 — Evaluation** (`autoform/eval/`). Phase 1 repo gate: `lake build` plus a forbidden-keyword scan (`elab`/`macro`/`syntax` — anti-compiler-tampering). Phase 2 per statement: (a) a **matcher** agent locates the Lean declaration (with an axiom-validation retry loop on `DeclarationNotFoundError`); (b) **axiom check** via `#print axioms` — anything beyond `propext`/`Classical.choice`/`Quot.sound` is flagged (notably `sorryAx`); (c) an **LLM jury**, one judge per JSON rubric: faithfulness (w=0.4, pass≥4/5), proof_integrity (0.4, ≥3), code_quality (0.2, ≥3) — a statement passes only if every rubric clears its threshold. Judges have access to a **declaration-level dependency graph** built by a Lean metaprogram that tags deceptive bodies (`vacuous_body`, `proof_by_exfalso`, `ignores_params`, `trivial_instance`, orphan classes) and computes transitive support cones with alerts. **Inherited-failure analysis** flips failures whose only unjustified axioms come from upstream evaluated statements. Phase 3: `report.json`/`report.md` + `failed_targets.yaml`, updated atomically and progressively. `EvalGate` exposes the same machinery as an in-pipeline merge gate.

Notably, the non-plugins fork already integrates **Aristotle two ways** (`docs/pipeline/aristotle_worker.md`): Mode A as a served "model," and Mode B as `AristotleAgent` — a duck-typed worker whose `call()` bundles the worktree, submits, lands the tarball, commits; the rest of the pipeline (build gate, merge queue, eval) is author-agnostic. The plugins fork dropped Aristotle.

## 2. Comparative inventory

**autoform has, marathon lacks:**
- **Per-statement data model.** Marathon's unit is the *chapter* (`order.txt` with free-form per-chapter instructions); autoform's is the *statement* (`targets.yaml`), enabling coverage accounting ("42 targets, 35 passed").
- **Orchestrator + task DAG** with dependency edges, automatic re-planning, decomposition, and auto-created fix tasks. Marathon's loops are linear (chapter order; fixed `--max-iterations`).
- **Matcher** (statement → declaration mapping) and **goal tracker** — marathon has no ground-truth "is theorem X done" signal beyond `lake build` and subjective ratings.
- **Hard verification machinery:** `#print axioms` checking, forbidden-keyword gate, dependency graph with deception tags, support-cone alerts, inherited-failure logic.
- **Thresholded jury judging** vs marathon's advisory 1–5 `--auto-rate` scores (no pass/fail semantics).
- **Parallelism at scale:** worktree-isolated worker racing, merge queue, multi-node SLURM, visualizer dashboard.
- **Accumulated machine memory per task** (trace analyzer → task skills); marathon's analog is the single repo-wide `referee.md`.

**marathon has, autoform lacks:**
- **Production-hardened Aristotle driving** (`aristotle_runtime.py`): status-aware retries with continuation context, reattach via `Project.from_id` after crashes, `OUT_OF_BUDGET`/`CANCELED` semantics, dashboard `PromptLog.md` — more battle-tested than autoform's demo-grade Mode B.
- **The GitHub-issue review loop** (`marathon/review/`): one sub-issue per declaration, `verify`/`reject --notes`, a single-flight **auto-refine daemon** that converts rejections into targeted `refine --review-rejection` Aristotle runs. This is the human-verification surface autoform entirely lacks (its only human touchpoint is the escalation log).
- **Referee mechanism:** human-pinned header + machine-managed tail of project-specific reviewer priorities, refreshed by an agent, fed to every review.
- **Information firewall:** Claude never sees the `.tex` (copyright confinement), Aristotle never sees `referee.md` — autoform's agents all read the book directly.
- **In-flight steering** (`hermes_watcher.py`) of running Aristotle jobs; cross-chapter context aggregation; Claude-Max-billed CLI subprocess (zero marginal token cost).

## 3. Integration opportunities for hands-off "point at a textbook" mode

1. **Adopt `targets.yaml` as marathon's ledger.** Run autoform's extraction once per book; derive `order.txt` per-chapter instruction blocks from targets grouped by `location`. Marathon then tracks per-statement (not per-chapter) progress in `marathon-state.json`.
2. **Vendor the matcher + axiom checker as the post-extraction truth signal.** After each `--auto-build`, run matcher → `#print axioms` per target. This replaces "build passed" with "target N is matched, sorry-free, axiom-clean" — exactly what `--auto-rate` can't tell you. The retry-on-unresolved-name loop ports directly.
3. **Swap the jury in for/alongside `--auto-rate`.** The `autoform:eval-rubrics` skill already bridges both vocabularies (jury rubrics + marathon's 7-dimension rater). Thresholded faithfulness/proof_integrity/code_quality scores give pass/fail; jury feedback strings are ready-made `reject --notes` payloads.
4. **Auto-populate the review loop from eval output.** `review bootstrap-chapter` should seed sub-issues from targets + match results, embedding the jury scorecard, axiom set, and cone alerts in each body. Then: **failures never reach a human** (jury feedback → daemon → refine), and humans only spot-verify jury-passed declarations — the minimal-surface gate. Inherited-failure analysis prevents duplicate rejections for one upstream sorry.
5. **Feed dependency-graph deception tags into the referee tail**, so Hermes' next prompts target `vacuous_body`/`ignores_params` structurally rather than cosmetically (this also strengthens `structural_focus` scoring against real diffs).
6. **Longer term, converge on autoform's seam:** autoform-bot's Mode-B `AristotleAgent` proves the orchestrator/DAG/merge-eval layers are worker-agnostic. Marathon could either absorb a lightweight `ItemTracker`-style DAG (fix tasks per sorry/axiom, like meval triage) or be mounted *as* the Aristotle worker tier under autoform's coordinator — with marathon contributing the retry/reattach/steering runtime, the firewall, and the GitHub human gate that autoform is missing.
